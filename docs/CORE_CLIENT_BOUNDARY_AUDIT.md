# Core / Client Boundary Audit

## Versioning

Basilisk game development and simulator-bot development use separate version lines.

- **Game:** pre-alpha `v0.x`
- **Simulation benchmark:** **BOT V3.14** is the current frozen balance/regression baseline.

Simulator version numbers describe bot/telemetry experiments only. They are not game versions.

## Goal

Move Basilisk from a simulation-first project toward a playable game without changing the proven V3.14 balance behavior unintentionally.

The Core must remain authoritative for rules, hidden state, legal actions, deterministic resolution, and player-visible snapshots. Clients should only present state and submit legal player actions. The simulator may choose actions and collect telemetry, but it must not define game rules that a human client would not share.

## Current boundary: what is already good

### Core owns authoritative match state

`MatchState` remains inside Core. Clients receive `PlayerRoundSnapshot`, not the raw world state.

### SnapshotSystem is the player-information boundary

`SnapshotSystem::buildForPlayer()` already constructs a viewer-specific snapshot containing:

- health / max health
- arrows / max arrows
- inventory
- current cave
- discovered map only
- local loose-arrow visibility only
- temporary Pit-map reveals
- legal available actions
- player observations
- Sigil possession
- extraction visibility according to reveal policy
- public match result

This is the correct architectural direction for future network clients.

### Legal actions are produced by Core

Clients do not need to recreate movement, shooting, item-use, or escape legality. `AvailableAction` is generated by Core and the client materializes one into `PlayerAction`.

### CLI already exercises a real human action loop

The current CLI:

1. Requests a player snapshot.
2. Displays only that player's visible state.
3. Presents Core-generated legal actions.
4. Collects actions from living hunters.
5. Resolves the simultaneous round through Core.
6. Repeats until the match ends.

This is a strong foundation for the first playable prototype.

### One SDL3 source now targets native desktop and the browser

The opt-in `BasiliskGame` target in `clients/game` links `BasiliskCore` and
uses SDL3 main callbacks. SDL3 3.4.10 is pinned through CMake FetchContent, and
the same C++ source has been proven as both a native application and an
Emscripten/WebAssembly browser application:

```text
BasiliskCore
    |
clients/game (C++ / SDL3)
    |
    +-- native desktop
    +-- Emscripten / WebAssembly browser
```

This target is intentionally only a graphical foundation today: it creates a
window and renderer, runs the callback lifecycle, and demonstrates a safe Core
link. Future presentation must consume `PlayerRoundSnapshot` and Core-produced
legal actions; it must not expose `MatchState`.

`clients/web-debug` remains useful as a developer debug and acceptance harness.
It is not the architecture for the shipping browser UI and should not be
ported into `clients/game` wholesale.

## Audit findings / work items

### P0 — freeze BOT V3.14 as regression benchmark

Do not delete or rebalance the V3.14 simulator while this architecture phase is underway.

Recommended regression command:

```bash
./build/clients/sim/BasiliskSim 1000 250 100000 500000
```

Architectural changes should be compared against the frozen seeded baseline. Expected values may change only when a deliberate gameplay change is approved.

### P0 — Core must remain the only rule authority

Review every decision helper in `clients/sim` and classify it as either:

- **bot strategy** — allowed to remain client-side, or
- **game rule / legal-action rule** — must live in Core.

The simulator is allowed to know its own memory and strategy. It should not need authoritative Basilisk, Pit, Jackal, rival, or loot state that is absent from `PlayerRoundSnapshot`.

### P0 — test the real dispatch path for every item/action

The Old Hunter's Map bug demonstrated that direct subsystem unit tests are insufficient when `TurnResolver` dispatch can differ.

For every action family, maintain at least one test that executes through the same public resolution path used by clients:

- Move
- Search
- Shoot
- UseItem (ordinary and world-aware)
- Contextual actions / extraction

### P1 — formalize the player-facing snapshot contract

`PlayerRoundSnapshot` should become the explicit client contract. Audit each field for whether it is:

- always visible,
- conditionally visible,
- event-only / transient,
- private to the viewing hunter,
- safe to serialize across a network.

Avoid exposing raw Core state to future clients.

### P1 — audit observations for information leakage

Each `PlayerObservation` must be derivable from information the player is entitled to know. In particular, verify:

- Basilisk clues never reveal exact hidden location unless a mechanic explicitly permits it.
- Rival location remains hidden except through intended clues/events.
- Pit identity/direction follows investigation and temporary-reveal rules.
- Loose arrows remain local-only unless remembered by the client/bot from prior legitimate observations.
- Extraction visibility follows `ExtractionRevealPolicy`.

### P1 — remove duplicate presentation mappings over time

Item names and observation strings currently live in the CLI, while simulator files also contain their own item-name helpers. These are presentation concerns, but repeated mappings are easy to let drift when new items are added.

Before adding gameplay presentation to the graphical client, introduce a small presentation/shared-client layer or stable IDs so each client does not need to maintain separate exhaustive mappings manually.

### P1 — make CLI the first playable acceptance client

Before implementing graphical gameplay or a server transport, the CLI should support a complete understandable game without developer knowledge.

Acceptance target:

- start a seeded or random match
- understand the current cave and exits
- understand warnings and observations
- inspect inventory
- choose every legal action type
- understand HP/ammo changes
- understand death and rival-death state
- recover a Sigil
- find/reach extraction when visible
- kill/evade the Basilisk
- complete a full match without consulting source code

### P2 — separate local orchestration from future authoritative server orchestration

The CLI currently owns the local loop, while Core owns resolution. Preserve that split.

Future server responsibilities should include:

- match/session ownership
- server-selected seeds / RNG authority
- player authentication / assignment
- simultaneous action collection
- timeout / reserve handling
- reconnect handling
- snapshot serialization
- event/observation delivery

Do not move those concerns into game-rule systems.

### P2 — define serialized protocol DTOs only after the CLI contract stabilizes

Do not serialize `MatchState` directly. Build network DTOs from the same player-facing contract represented by `PlayerRoundSnapshot`, legal actions, observations, and public match status.

## First implementation phase

1. Keep BOT V3.14 frozen.
2. Treat game development as pre-alpha `v0.x`.
3. Add boundary/regression tests before large refactors.
4. Keep upgrading the CLI as the first playable acceptance client.
5. Grow `clients/game` from its proven native/browser SDL3 foundation using only player-safe snapshots and legal actions.
6. Human-playtest before designing the final graphical gameplay interface or multiplayer protocol.

## Definition of success for this phase

The phase is complete when a human can play repeated full matches through a player-facing client using only information supplied by Core, while the frozen V3.14 seeded simulator remains behaviorally stable except for explicitly approved gameplay changes. The current SDL3 target proves portability and lifecycle integration only; it does not yet meet that gameplay criterion.
